# windows/tui-desktop

Общий контракт окон: [SDK оболочки Windows](https://github.com/wippy-windows/windows/blob/main/docs/sdk.md).
В основе находятся `window_api`, `geometry`, `input` и `scroll`; готовые
декларативные компоненты и навык — в модуле `windows/shell`.


Оконный менеджер для терминала на рантайме Wippy.

Один процесс-композитор владеет физическим экраном и рисует окна; каждое окно —
отдельный процесс, который пишет в собственный viewport через обычный `tty` и
считает, что владеет терминалом целиком. Ни одно окно не знает, что оно окно:
поэтому в окне работает настоящий `bash`, `htop`, редактор или Claude Code —
без единой строчки, написанной под этот десктоп.

Тем же экраном одновременно управляет агент: у модуля есть HTTP-канал, которым
можно открыть окно, переставить его, напечатать в него и **прочитать его экран**.

```
физический TTY → surface композитора → viewport → процесс окна → PTY-прокси → программа
```

## Из чего это состоит

Четыре части, и граница между ними — то, ради чего модуль устроен так, а не
проще.

- Часть: **Механика**; Что это: `…desktop:library` — одна функция `run(options)`: окна в z-порядке, ввод, хит-тест, командный канал, хостинг процессов; Кто её пишет: этот модуль
- Часть: **Оболочка**; Что это: процесс, который зовёт `run` со своей темой, каталогом и раскладкой стола; Кто её пишет: приложение; здесь их две — штатная и Windows 95 в `windows/shell`
- Часть: **Тема**; Что это: чистые функции рисования: рамки, полосы, меню, значки. Возвращает разметку попаданий; Кто её пишет: оболочка
- Часть: **Окно**; Что это: запись реестра. Обычно процесс, который пишет в свой viewport и не знает, что он окно; бывает и вид без процесса; Кто её пишет: приложение

**Механика не знает, как выглядит вид, а тема не знает, что происходит.**
Композитор считает координаты и состояние, тема кладёт краски и возвращает,
куда попадает щелчок. Поэтому вторая оболочка получает другой вид, не копируя
ни хостинг окон, ни PTY, ни командный канал, — и поэтому же в этом README так
много про то, кто кому что отдаёт.

Кадр собирается так — и порядок шагов важнее, чем кажется:

1. композитор чистит канву и просит тему залить стол (`fill`);
2. кладёт содержимое окон — в режиме символов это делает тема вместе с рамкой,
   в пиксельном композитор сам;
3. просит тему нарисовать хром: в ячейках — `window`, `bars`, `menu`; в
   пикселях — один `paint`, возвращающий растры;
4. отдаёт кадр поверхности: `present(rows)` или `present(rows, {images})`.

С чего начинать чтение, смотря зачем пришли:

- **объявить окно в своём приложении** — «Окна приносит приложение»;
- **написать оболочку или тему** — «Вид отделён от механики: контракт темы», и
  сразу за ним «Пиксельный хром», если рисовать растрами;
- **разобраться, почему что-то не работает** — «Разработка»: там правила,
  которыми это ловится, и симптомы, которые не похожи на свои причины.

## Что нужно

- Wippy **0.3.40a** или новее — модуль `tty` появился там (#631, фиксы в #637).
- Приложение Kickside, дающее `app:api` (роутер с аутентификацией).

## Запуск

```bash
wippy run --host windows.tui_desktop:terminal desktop
```

`--host` здесь обязателен, и это не придирка: автодетект терминального хоста в
CLI — просто подсчёт записей `terminal.host` во всём реестре, а этот модуль
приносит вторую. С момента установки **каждая** команда приложения требует
явного `--host`; соседние команды выбирают хост приложения
(`--host wippy.terminal:host`).

Собственный хост нужен ради `hide_logs`. Диффер поверхности считает себя
единственным писателем в терминал, поэтому строка лога разъезжает кадр
насовсем — неизменившиеся строки не перерисовываются. Забрать под это хост
приложения нельзя: на нём живут фоновые процессы, и приложение лишилось бы лога.

### Окружение Bash

Штатное окно запускает `/bin/bash -i`, поэтому читает `~/.bashrc`:
пользовательские пути, nvm и другие настройки работают и в окне.
`exec.native` передаёт только явно заданное окружение. Приложение задаёт
`HOME` и `PATH` именно исполнителю терминальных окон в `.wippy.yaml`:

```yaml
override:
  "windows.tui_desktop:exec:default_env.HOME": "${env:HOME}"
  "windows.tui_desktop:exec:default_env.PATH": "${env:PATH}"
```

Это значения окружения процесса, запускающего Wippy; имена пользователей
и пути к установленным программам в модуле не зашиты. `TERM` уже задан
исполнителем. После изменения `.wippy.yaml` нужен перезапуск приложения.
Проверка внутри окна: `command -v claude codex`. Программы должны быть
установлены у того же пользователя ОС, под которым работает Wippy.

### Клавиши

- `alt+n` — новое окно с интерактивным bash
- `alt+o` — меню окон, которые объявило приложение
- `alt+w` — закрыть текущее окно
- `alt+m` — свернуть текущее окно
- `alt+tab` — следующее окно
- `ctrl+q` — закрыть все окна и выйти

В открытом меню — стрелки и `enter`: `↑`/`↓` водят курсор по строкам, `→`
раскрывает папку, `←` возвращает на уровень выше, `enter` открывает, `esc`
закрывает. **Курсор ходит по РАЗМЕТКЕ, а не по каталогу**: тема помечает
выбранную строку (`cursor = true`), композитор открывает помеченную. Считать
выбор с двух сторон значило бы завести два мнения о том, что выбрано, и
однажды они разойдутся.

Когда ни одно окно не в фокусе, стрелки водят выделение по значкам стола, а
`enter` открывает выделенный. **При окне в фокусе стол стрелки не берёт** —
иначе редактор внутри окна лишился бы стрелок.

Цифровых сокращений нет и не будет: `alt+1`…`alt+9` и «цифра — открыть» в меню
убраны. Правило — **клавиатурных путей, не видных в интерфейсе, не заводить**;
а видный путь требует колонки цифр на экране, которой в Windows 95 нет.

Всё остальное уходит внутрь окна. Акселераторы держатся на `alt` нарочно:
`ctrl` и `tab` слишком часто нужны самим программам, и красть их — значит
ломать редактор внутри.

Мышью можно перетащить окно за заголовок, потянуть за правый нижний угол,
нажать `[-]`, `[□]`, `[×]` и переключиться по вкладке сверху. Включённая мышь
забирает у терминала обычное выделение текста — для копирования держите Shift.
The size handle is the last two cells of the bottom frame row, where a theme
draws the Windows 95 sizing grip; the window keeps the pointer's offset from
the corner while it is dragged, and a window with `resizable: false` ignores
the handle.

## Командный канал

Все ручки живут за аутентифицированным роутером приложения.

- `GET /tui-desktop/windows` — открытые окна, фокус, размер экрана и состояние стола (см. ниже)
- `POST /tui-desktop/windows` — открыть окно: `entry`, `command`, `title`, `x`, `y`, `w`, `h`
- `POST /tui-desktop/windows/{id}/type` — напечатать `text`, при `enter: true` с переводом строки
- `POST /tui-desktop/windows/{id}/key` — одна клавиша: `key`, `ctrl`, `alt`, `shift`
- `POST /tui-desktop/windows/{id}/screen` — содержимое окна строками
- `POST /tui-desktop/windows/{id}/move` — переставить: `x`, `y`
- `POST /tui-desktop/windows/{id}/resize` — размер: `w`, `h`
- `POST /tui-desktop/windows/{id}/focus` — поднять наверх
- `POST /tui-desktop/windows/{id}/minimize` — свернуть или развернуть: `value`
- `POST /tui-desktop/windows/{id}/close` — закрыть

Мастерская — окна, собранные на ходу:

- `POST /tui-desktop/apps` — собрать окно: `name`, `source`, `title`, `width`, `height`, `modules`, `group` (папка меню, как `meta.group` у записи из файла; пусто — папку выбирает оболочка). Сверх кода — те же поля, что у записи из файла: `imports` (`{имя = id библиотеки}`, имя `desktop` занято), `pixel_render` (библиотека пиксельного вида; `pixel_state` — само окно), `image`, `icon`, `window_type` (`app | dialog | tool`), `resizable`, `in_menu`, `order`. Так в мастерской собирается окно на SDK оболочки: `imports = {app = "windows.shell.sdk:app"}`, `pixel_render = "windows.shell.sdk:render"`. Мёртвый импорт и не-библиотека отклоняются по имени поля
- `GET /tui-desktop/apps` — сохранённые окна и признак `live` (есть ли запись в реестре сейчас)
- команда `desktop.tray` `{key, text, entry?, title?, ttl?}` командного канала — пункт области уведомлений у часов; тот же `key` обновляет, `{key, remove: true}` снимает. Не больше 6 пунктов и 16 знаков в подписи. Пункт, не обновлённый за `ttl` секунд, композитор снимает сам. Щелчок по пункту открывает `entry` или поднимает уже открытое окно — как щелчок по часам. Из Lua — `window_api.tray(spec, service?)`; `desktop.list` отдаёт `tray` с владельцем и остатком срока
- command `desktop.refresh` of the command channel also brings the desktop widgets in line with `options.widgets`: new entries are spawned, vanished ones stopped, stopped ones spawned again; `desktop.list` returns `widgets` — `{id, entry, title, opens, w, h, revision, waiting, stopped}` each, without the tree. See "Desktop widgets"
- команда `desktop.workshop` `{name, remove?}` командного канала — применить сохранённое окно в реестр (или снять) силами композитора: так окно собирает туз MCP, чей скоуп запрещает `registry.apply`
- `DELETE /tui-desktop/apps/{name}` — убрать окно из хранилища и реестра

Префикс пути задаёт роутер приложения, а не модуль: `/api/v1` на стенде
kickside, `/api` в харнессе. Промах отдаёт страницу фасада с кодом 200, поэтому
проверять стоит по `content-type`, а не по коду.

```bash
curl -X POST -H 'Content-Type: application/json' \
  -d '{"title":"сборка","command":"/bin/bash -i"}' \
  http://localhost:8099/api/v1/tui-desktop/windows

curl -X POST -H 'Content-Type: application/json' \
  -d '{"text":"make test","enter":true}' \
  http://localhost:8099/api/v1/tui-desktop/windows/w1/type

curl -X POST -H 'Content-Type: application/json' -d '{}' \
  http://localhost:8099/api/v1/tui-desktop/windows/w1/screen
```

Команды без ответа не бывает: молчание композитора невозможно отличить от
применённой команды, и вызывающий поверил бы в успех. Незапущенный десктоп и
неотвечающий десктоп — тоже разные ответы.

**`GET /tui-desktop/windows` — это ещё и приборная доска.** Каждое поле в ней
появилось потому, что без него два разных состояния выглядели снаружи
одинаково, и на различении экономился час:

- Поле: `notice`; Что различает: строка состояния — то, что видит человек. Отказ на команду, которой никто не ждал, виден только здесь
- Поле: `menu_open`; Что различает: «щелчок по кнопке меню не дошёл» против «дошёл, а меню не нарисовалось»
- Поле: `menu_path`; Что различает: раскрытая папка меню: «стрелка вправо не сработала» против «сработала, а подменю не нарисовалось»
- Поле: `menu_choices`, `menu_folders`; Что различает: сколько строк на уровне и сколько раскрывается. Ноль папок означает «раскрывать нечего», а не «сломано»
- Поле: `menu_cursor`; Что различает: номер выбранной строки на текущем уровне, 0 — не выбрано: «наведение не выделило» против «выделило, а тема не нарисовала»
- Поле: `selected`; Что различает: выделенный значок стола: «стрелка не сработала» против «тема не нарисовала выделение»
- Поле: `pixels`; Что различает: в каком режиме композитор рисует
- Поле: `frame`; Что различает: цена последнего кадра: `changed_rows`, `bytes_written`, `images` и `placements_sent`. Неверно порезанный хром рисует ПРАВИЛЬНЫЙ экран, просто медленный
- Поле: `restore`; Что различает: что стало с окнами мастерской на старте: молчание читалось бы как «окон не было»

У окна в списке, кроме геометрии: `window_type`, `opened_by` (кем открыто),
`content` (`cells` или `pixels`), `waiting` и `state_revision` — для окна-вида,
ждёт ли оно первого состояния.

Оговорка про проверки: **ручки этого модуля не вызываются по HTTP ни одной
проверкой** — харнесс поднимает роутер только затем, чтобы записи разрешились,
а аутентификации в нём нет. Форма ручек проверяется как проводка (запись,
обработчик, метод, путь, политика), а ответ композитора — живым композитором.
Первый настоящий вызов ручки — всегда с живого стенда.

## Окна приносит приложение

Модуль знает ровно одно своё окно — программу под PTY. Всё остальное объявляет
приложение записью процесса, которая умеет писать в свой `tty`-порт; пометка
`meta.type: tui_desktop.window` кладёт её в меню `alt+o`, а `meta.title`,
`meta.width` и `meta.height` говорят, как её открыть. Ни строчки в этом модуле
править для нового окна не нужно — иначе каждое приложение требовало бы релиза
десктопа.

Ещё два поля описывают, чем окно является и где его искать:

- Поле: `meta.window_type`; По умолчанию: `app`; Смысл: `app`, `dialog` или `tool` — по нему тема выбирает состав кнопок заголовка
- Поле: `meta.in_menu`; По умолчанию: `true`; Смысл: `false` прячет программу из «Пуска», не мешая открыть её ярлыком или из другого окна
- Опция композитора `desktop_properties` (идентификатор записи): окно свойств самого стола — «Свойства» по правой кнопке на пустом месте. `desktop.list` отдаёт `screen`, `cell = {w, h}` в пикселях и `pixels` — режим кадра; окно свойств экрана показывает разрешение по ним
- Поле: `meta.properties`; По умолчанию: нет; Смысл: идентификатор записи окна свойств программы — пункт «Свойства» в контекстном меню её значка на столе (правая кнопка). Нет поля — нет пункта
- Поле: `meta.resizable`; По умолчанию: `true`; Смысл: `false` — размер фиксирован: окно открывается ровно с `width`×`height` записи, даже если открывающий просил другой размер или не просил никакого; угол не тянется, кнопки «развернуть» нет, `desktop.resize` отвечает отказом. Для окон, чья раскладка посчитана под один размер

- **Неизвестный тип — это `app` и предупреждение в лог**, а не спрятанная
  программа: запись объявил кто-то другой, и опечатка в одном поле не повод не
  показать окно, которое в остальном исправно.
- **Признак, а не вывод из типа.** Диалог в меню не нужен почти никогда, но
  «почти» тут дорого стоит: «О программе» — диалог, и его место как раз в меню.
- **Прячется меню, а не запуск.** `in_menu: false` не мешает ни ярлыку на
  столе, ни `desktop.open` из соседнего окна, ни командному каналу.

```yaml
- name: window_calc
  kind: process.lua
  meta:
    type: tui_desktop.window
    title: Калькулятор
    width: 28
    height: 15
  source: file://window_calc.lua
  method: main
  modules: [channel, tty]
```

Такое окно открывает поверхность своего порта и публикует кадры — в отличие от
окна с программой, где аренду порта забирает себе PTY-сессия. Через командный
канал оно открывается по имени записи: `{"entry": "app.desktop:window_calc"}`.

## Окно можно собрать в работающем рантайме

Реестр меняется на живую (`snapshot → changes → apply`), поэтому окно не обязано
быть файлом: его код едет в теле запроса, и окно появляется в меню сразу — без
перезапуска.

```bash
curl -X POST -H 'Content-Type: application/json' \
  -d '{"name":"clock","title":"Часы","width":30,"height":6,
       "modules":["time"],"source":"…lua…"}' \
  http://localhost:8099/api/v1/tui-desktop/apps
```

Исходник при этом ложится в таблицу `windows_tui_desktop_windows`, и на
старте композитор возвращает сохранённые окна в реестр. Без этого собранное
окно жило бы ровно до конца процесса.

Восстанавливает именно композитор, а не фоновый сервис, и это не выбор стиля:
платформа намеренно запрещает процессам группы `wippy.security:process` менять
реестр — политика `wippy.security:registry.no_write` перекрывает разрешения
явным `deny`, и такой сервис молча не делал бы ничего. Композитор работает под
собственным актором, а нужны эти окна ровно тогда, когда десктоп запущен.

Итог восстановления виден снаружи — `GET /tui-desktop/windows` отдаёт поле
`restore` (`restored`, `failed`, `names`, `error`). Лог терминального хоста
заглушён, иначе он разъедет кадр, поэтому отказ, рассказанный только в лог, не
рассказан никому.

- **Одна строка на окно, имя — ключ.** Повторная сборка перезаписывает: история
  правок не ведётся, а «имя занято» было бы отказом чинить собственное окно.
- **Сборка окна одна на оба пути.** Мастерская и загрузчик строят запись одним
  и тем же кодом — разойдись они, окно вело бы себя по-разному до и после
  перезапуска, а такое расхождение проявляется через сутки.
- **Модули окна выбираются из белого списка**: `channel`, `time`, `tty`,
  `json`, `sql`; `tty` и `channel` добавляются всегда. `env` в списке был и
  убран: права `env.get` у окна нет, а без права `env.get` отдаёт nil вместо
  громкого отказа — и соседнее `or умолчание` превращает отказ по правам в
  «никто ничего не назначал». Выдать право было бы хуже: код окна приезжает по
  HTTP, а в окружении лежат токены. Запрошенный
  модуль вне списка — отказ с его именем, а не молчаливое игнорирование.
  Порождать процессы и запускать программы окну нечем: код приходит по HTTP,
  и права выданы ровно под рисование и чтение данных.
- **Импорт — любая библиотека реестра, и это не дыра.** Права окну даёт его
  политика и скоуп, под которым его породил композитор; библиотека своих
  прав не приносит. Поэтому окно из мастерской вправе импортировать SDK
  оболочки — и рисоваться общим отрисовщиком, в пикселях, как окно из файла.
  Описание хранится колонкой `spec` (миграция 03), собирается тем же
  `build_entry`, что и раньше; разбор тела — `apps.prepare`, один на HTTP и
  на туз MCP.
- **Библиотека получает СВОИ модули, а не модули окна.** Список у записи окна
  ограничивает код самого окна; библиотека, которую окно импортирует, работает
  со списком, объявленным у неё. Поэтому `desktop` читает имя композитора
  модулем `ctx`, которого в белом списке окна нет, и ни одно существующее окно
  править не пришлось. Комментарий в `apps.lua` про «библиотеке нужен process»
  читается наоборот — он про удобство самого окна, а не про требование
  библиотеки. Доказательство лежит тестом: `app:window_probe_bare` объявляет
  только `process` и всё равно получает имя.
- **Удаление не гасит открытые окна.** Процесс живёт своей жизнью; удалена
  возможность открыть новое, и ответ говорит об этом прямо.

## Окно узнаёт своего композитора при запуске

Имя композитора едет окну в контексте процесса: композитор кладёт его при
`spawn` под ключом `tui_desktop.service`, а библиотека `desktop` читает оттуда.
Раньше имя было константой, и под второй оболочкой окно обращалось к чужому
(несуществующему) процессу — молча, потому что `desktop.open` ответа не ждёт.

- **Ключ один на обе стороны.** Механика берёт его у `window_api`, а не
  повторяет строкой: разойдись они, окно снова взяло бы штатное имя, и вернулся
  бы ровно тот дефект, который здесь починен.
- **Модуль `ctx` объявляет библиотека, а не запись окна.** Библиотека получает
  свои модули, поэтому окна, написанные до этого поля, и окна из мастерской (у
  неё узкий белый список) получают имя без единой правки. Проверено тестом на
  живом запуске, а не выведено.
- **Окно, запущенное без имени, работает как раньше** — берёт штатное
  `windows.tui_desktop.desktop`.
- **Отказ называет причину и уходит в лог.** «Десктоп такой-то не отвечает;
  имя композитора не пришло при запуске» — во втором возвращаемом значении и
  строкой в логе: `open` ответа не ждёт, и окно, не проверившее возврат, иначе
  не рассказало бы об отказе никак.

## Окно может попросить десктоп

Клики и клавиши доезжают до окна как есть — композитор транслирует их в его
координаты. Обратный путь даёт библиотека `desktop`, которую мастерская
подключает каждому собранному окну:

```lua
local desktop = require("desktop")

desktop.open({entry = "…:dataflow_detail", title = "Узлы", args = flow_id, w = 86, h = 18})
desktop.focus(id)
desktop.close(id)
```

A close is a **request**: the title bar's ×, ctrl+w and a plain `desktop.close`
send the window `close` and wait for it to close itself. A window may refuse —
an application with a changed document asks first — and when the grace (3 s)
runs out without it closing, it stays open and the status line says
"<title> did not close" (`desktop.list` reports it as `notice`). Shutdown
(ctrl+q, Shut Down) and `desktop.close{id, force = true}` do not ask: they kill
the window after the grace, as every close did before. A PTY window has no loop
to answer, so every close of it is forced. A window may also refuse at once: its
own process answers `close` with `desktop.close{refused = true}`
(`window_api.close(id, {refused = true})`; a cells window passes no id — its
process names it), the request is over without the notice, and a later ×
asks again; from any other process such a refusal is refused.

Так виджет становится действующим: клик по строке открывает соседнее окно с
параметром. Окно-приложение получает свой параметр как `args`; `command`
остаётся программой для PTY-окна — одно поле на оба смысла читалось бы как
«команда», и окно подробностей открывали бы строкой `/bin/bash`.

Граница при этом узкая и проверяется тестом: окно умеет **попросить**
(`process.send` и найти адресата), но `spawn`, `exec` и `registry.apply` ему не
выданы. Присланный по HTTP код может дёргать ровно те команды десктопа, что и
так открыты снаружи, — и ничего сверх.

Ответа `desktop.open` не ждёт намеренно: ожидание чужого ответа заморозило бы
кадр окна, а что окно открылось, видно на экране. Когда ответ всё-таки нужен —
`desktop.open_wait` (то же самое, но с описанием открытого окна, включая `id`),
`desktop.ask` и `desktop.replies()`, см. ниже: они не читают inbox и потому не
съедают чужих сообщений.

## Окно может спросить, не потеряв команду

Описание окна в ответах `desktop.open` и `desktop.list` включает `image` —
имя значка, выбранное при открытии из `meta.image` или параметров окна.
Списки приложений используют его же, что заголовок и панель задач.

The window description also carries `args` — the argument the window was
opened with (`desktop.open{args = …}`), absent when there was none. An opener
finds a window already open for the same thing by `entry` and `args` and sends
`desktop.focus` instead of opening a second one: a folder window for the same
path is raised, as in Windows 95. A bash window's command stays in `command`.


Вопрос с ответом — `desktop.ask` (ждёт) или `desktop.request` + `desktop.replies()`
(не ждёт). Ответ приходит **своим каналом**, а не в общий inbox, и в этом всё
дело.

```lua
local desktop = require("desktop")

-- окно со своим циклом: канал ответов ложится в select рядом с событиями
local replies = desktop.replies()
desktop.request("desktop.list", {})

-- простой случай: подождать ответ на месте
local answer, err = desktop.ask("desktop.list", {}, {timeout = "2s"})
```

Почему не циклом по inbox, как делает командный канал снаружи: **такой цикл
забирает из inbox всё подряд и выбрасывает то, что не его ответ**, а окну через
тот же inbox приходят чужие сообщения. Измерено на живом запуске: команда
`desktop.close`, посланная окну, пока оно ждало ответ, исчезала без следа —
снаружи это выглядит как окно, переставшее слушаться мышь, и искать будут в
композиторе. Проверка на «ответ пришёл» такую потерю не видит: ответ приходит
в обоих случаях. Поэтому тест проверяет судьбу КОМАНДЫ, и рядом лежит второй,
показывающий тот же сценарий наивным циклом.

Что при этом делает рантайм — тоже измерено, и это важно для читателя:

- **Сообщение, которому некому отдаться, не теряется.** Оно ждёт в очереди
  процесса, пока окно не вернётся к своему `select`. Значит достаточно НЕ
  забирать чужое из inbox; возвращать ничего не нужно, потому что оттуда
  ничего и не взяли. Механика этого — `subs.match(topic)` в
  `runtime/lua/engine/process.go`: сообщение отдаётся подписке на ТОЧНЫЙ топик,
  а inbox — только запасной путь для тех, у кого своей подписки нет; кому
  отдать некому, тот остаётся в очереди. Отсюда общее правило, которым стоит
  мерить такие баги: **теряет пользовательский код, а не рантайм** — искать
  надо цикл, который прочитал и выбросил.
- **События viewport переживают занятое окно.** Клавиши, отправленные окну,
  которое 1.2 с ничего не читало, дошли все и по порядку. Поэтому `ask` не
  теряет ни ввода, ни `close` — но кадр на время ожидания стоит, и срок у
  ожидания есть всегда (`api.BUDGET`, по умолчанию 5 с).
- **Ответ, которого не дождались, выбрасывается перед следующим вопросом.**
  Корреляции у ответов нет, и прочитанный как свежий он ответил бы на прошлый
  вопрос вместо нынешнего. Выбросить ответ безопасно — в отличие от команды.

### Отказ доезжает до того, кто не ждал ответа

`close`, `focus` и `open` ответа не ждут — и всё же узнают об отказе. Композитор
знает отправителя команды, поэтому «нет окна w404» уходит ТРЕМ адресатам, и
каждый нужен своему читателю: строка состояния — человеку за столом, лог — тому,
кто разбирается потом, и сам отправитель — в его канал ответов.

```lua
{ok = false, error = "нет окна w404", command = "desktop.focus", unsolicited = true}
```

- **`unsolicited` обязателен.** Отказ, приехавший сам, встаёт в тот же канал,
  где окно ждёт ответы. Без пометки он был бы принят за ответ на следующий
  вопрос — то есть починка молчания родила бы враньё. `ask` такие сообщения
  пропускает, называя их в логе, и продолжает ждать своё.
- **Каждый ответ называет свою команду** (`command`). Сопоставление по одному
  лишь порядку ломается ровно тогда, когда в поток приходит что-то незваное.
- **Окну, которое канала не создавало**, отказ приходит обычным сообщением в
  inbox — его читает собственный цикл окна.

Окно, которое зовёт `ask` или `replies()`, перестаёт получать `desktop.reply`
в inbox: подписка на топик забирает его себе. Окно, разбиравшее ответы своим
циклом по inbox, менять не обязано — но смешивать оба способа в одном окне
нельзя.

## Диалог принадлежит окну, которое его открыло

```lua
local dialog, err = desktop.dialog({entry = "app.desktop:props", title = "Свойства"})
```

Композитор узнаёт родителя **по отправителю команды**, а не по номеру в
запросе: своего номера окно не знает, а присланный в поле чужой номер ничем не
проверить — так можно было бы объявить своим диалогом любое окно на столе.

Что из связи следует:

- Тип: `dialog`, `tool`; Поведение: встаёт по центру своего окна, держится поверх него, закрывается вместе с ним
- Тип: `app`; Поведение: ничего: программа, открытая из другого окна, живёт своей жизнью

- **Модальности нет, и это решение, а не недоделка.** Блокировать ввод
  остальных окон там, где окно — чужой процесс под PTY, значит уметь подвесить
  весь стол одной программой, которая не отвечает.
- **`opened_by` записывается всегда**, даже для обычной программы: «кто открыл»
  — это факт, а поведение выбирается типом. Поэтому просмотрщик, открытый из
  «Моего компьютера», не уйдёт вместе с ним.
- **Связь видна снаружи**: `GET /tui-desktop/windows` отдаёт `window_type` и
  `opened_by` на каждом окне. Без этого отладка идёт вслепую: диалог, который
  не закрылся с окном, и диалог, который никогда не был связан, выглядят
  одинаково.
- **Явные координаты сильнее центрирования**: их назвал тот, кто просил.
- **Каскад закрытия живёт в двух местах, и это не дубль.** Вежливое закрытие
  уносит диалоги сразу; второй каскад — на случай окна, умершего само, иначе
  диалог остался бы привязанным к номеру, которого больше нет.

## Окно-вид: процесса внутри нет

Запись объявляет, чем рисуется её содержимое. Умолчание — `cells`, то есть как
раньше: внутри процесс, он пишет в свой viewport.

```yaml
meta:
  type: tui_desktop.window
  window_content: pixels                        # cells (по умолчанию) | pixels
  render: windows.shell.explorer:render_pixels # чистая библиотека отрисовки
  state:  windows.shell.explorer:state     # процесс-поставщик, свой актор
```

`pixels` означает, что **процесса внутри нет**: рисует тема, зовя `render`,
а данные приносит отдельный процесс. Умолчание не вкус: чужая программа (bash,
htop) умеет выдавать только ячейки, и окно, чья запись про это поле молчит,
обязано вести себя как раньше — ошибиться в сторону `cells` значит потерять
красоту, ошибиться в сторону `pixels` значит потерять bash.

- **Два имени, а не одно: рисование в композиторе, права снаружи.** `render` —
  чистая функция без рантайма и без прав; `state` — процесс со своим узким
  актором, который добывает данные. Слей их в одно, и чтения проводника
  переехали бы процессу, который умеет порождать процессы и запускать
  программы.
- **Композитор `render` не зовёт и звать не может.** Ни создать растр (модуль
  `gfx` механике не объявлен, и объявить его нельзя — см. «Пиксельный хром»),
  ни загрузить библиотеку по имени из реестра: импорты объявляются записью.
  Поэтому композитор несёт **состояние** до темы, а зовёт `render` тема,
  которая его импортирует.
- **Состояние толкает поставщик, а не спрашивает композитор.** Композитор не
  знает, когда данные устарели, — знает тот, кто их читает; опрос на каждый
  кадр означал бы `registry.find` шестьдесят раз в секунду ради списка, который
  меняется раз в час. И кадр не должен ждать чужой процесс: задумавшийся
  поставщик заморозил бы весь стол.
- **Состояния ещё нет — вид говорит, что ждёт** (`waiting` в `desktop.list`), а
  не показывает вчерашнее и не висит.
- **Чужое состояние отвергается.** Принимается только от поставщика ЭТОГО окна:
  вид, нарисованный подложенными данными, от настоящего неотличим.
- **Ввод уходит поставщику** — живой части у такого окна больше нет, а вид —
  чистая функция и щелчок принять не может. Координаты те же, что у окна с
  процессом: относительно клиентской области внутри рамки.
- **Поставщик живёт при окне**: поднимается при открытии, гасится при закрытии,
  а его смерть видна в строке состояния — вид, застывший на последнем
  состоянии, выглядит живым и врёт тем убедительнее, чем дольше висит.
- **Мёртвая ссылка отказывает сразу.** Нет `render`, или запись по ссылке не
  существует — окно не открывается и говорит почему. Иначе пустое окно
  выглядело бы виной темы.

Для программы с двумя бэкендами вместо обязательного `window_content: pixels`
можно объявить `meta.pixel_render` и `meta.pixel_state`, сохранив основной
процесс в ячейках. Композитор выбирает эти ссылки только в пиксельном режиме,
если тема подтверждает `chrome.renders(pixel_render)`. Без подтверждения
запускается обычный процесс окна.

Поставщик состояния получает `main(service, window_id, args, viewport)`:
`args` — строка открытия, `viewport` — `{width, height, cell_w, cell_h}`.
Контекст `window_api.CONTEXT_KEY` содержит имя композитора. Публичные
`window_api.inputs()` и `input_event(message)` дают события `window.input`;
`publish_state(id, state)` отправляет состояние без запроса ответа. Если в
состоянии есть `title`, обновляется заголовок окна. Изменение размера
приходит событием `resize` с той же геометрией клиентской области.
A state's `image` (a picture name) replaces the window's title-bar picture the
same way, and `desktop.list` reports it; an absent or empty `image` keeps the
picture the window has — a folder window that navigates in place changes both.

## Вид отделён от механики: контракт темы

Композитор — библиотека `windows.tui_desktop.desktop:library` с одной
функцией `run(options)`. Всё, что рисуется, приходит темой в `options.chrome`;
геометрию хрома — сколько строк занято сверху и снизу — тоже объявляет она.
Штатная оболочка (`…:desktop`) зовёт `run` со своей темой; вторая оболочка
приносит другую и получает другой вид, не копируя ни хостинг окон, ни PTY,
ни командный канал.

```lua
local library = require("library")
local chrome = require("chrome")

local function main()
    -- Голым `return library.run(...)` это писать нельзя: в go-lua v1.5.18
    -- хвостовой вызов yield-функции из базового фрейма корутины не
    -- выполняется вовсе — молча, за 0 мс.
    local ok, err = library.run({chrome = chrome, service_name = "…"})
    return ok, err
end
```

`options`:

- Поле: `chrome`; Смысл: тема. Обязательна: композитор без вида — пустой экран, в котором нечего искать, поэтому отказ называет причину, а не подставляет тему молча
- Поле: `pixels`; Смысл: рисовать ли хром растрами. По умолчанию нет; см. «Пиксельный хром»
- Поле: `cell_size`; Смысл: `() -> w, h` либо `nil, причина` — размер ячейки в пикселях. Нужен только в пиксельном режиме
- Поле: `service_name`; Смысл: имя, под которым композитор виден процессам
- Поле: `hint`; Смысл: подсказка на пустом рабочем столе
- Поле: `catalog`; Смысл: `() -> items, failure` — каталог программ. По умолчанию внутренний, плоский
- Поле: `desktop_items`; Смысл: `() -> items, failure` — раскладка стола: ярлыки и папки. По умолчанию пусто
- Поле: `move_desktop_item`; Смысл: `(id, x, y) -> ok, error` — записать новое место значка. Композитор раскладку не пишет, а просит: отказ откатывает значок туда, откуда его взяли
- Поле: `restore`; Смысл: возвращать ли на старте окна мастерской в реестр; по умолчанию да
- Поле: `logon`; Смысл: `(screen) -> identity | nil, причина` — вход в систему до первого кадра стола. См. «Вход в систему»
- `widgets` — `() -> {{entry, title, w, h, order, opens}, …}, failure`: desktop widgets to spawn. None given — no widgets. See "Desktop widgets"

Тема — библиотека, возвращающая таблицу. Композитор зовёт только это:

- Функция: `layout(width, height)`; Обязана: вернуть `{top = N, bottom = M}` — сколько строк хром забирает сверху и снизу. Рабочий стол — строки `top + 1 .. height - bottom`
- Функция: `fill(canvas, width, height, state)`; Обязана: залить рабочий стол и нарисовать значки; вернуть разметку попаданий или ничего
- Функция: `window(canvas, window, focused)`; Обязана: нарисовать рамку, заголовок и содержимое окна
- Функция: `bars(canvas, width, height, state)`; Обязана: нарисовать полосы (полоса окон, панель задач, статус) и вернуть разметку попаданий
- Функция: `menu(canvas, width, height, items, failure, open, cursor, anchor)`; Обязана: нарисовать каталог программ и вернуть разметку попаданий; строку под курсором **пометить** `cursor = true`. С `anchor = {x, y}` это контекстное меню значка стола: плоский список у указателя, подпись пункта — `label` (у «Открыть» `title` — заголовок окна, которое пункт откроет), `bold` — действие по умолчанию, `separator_before` — черта над пунктом. В пиксельном режиме то же приходит полем `menu.anchor` состояния кадра. Открывает его композитор по правой кнопке на значке; пункты — «Открыть» и, если запись объявила `meta.properties`, «Свойства»; попадание значка (`hits.desktop`) обязано нести `properties`, иначе пункта не будет
- Функция: `empty_desktop(canvas, width, height, text)`; Обязана: подсказка на пустом столе
- Функция: `farewell(canvas, width, height)`; Обязана: необязательно: экран прощания после «Завершения работы» из меню — композитор показывает его, держит `FAREWELL_HOLD` секунд (по умолчанию 5) и только потом выходит; в пиксельном режиме может вернуть `{placements}`. Тема без него выходит сразу; ctrl+q экран не показывает
- Функция: `BUTTONS`, `BUTTONS_WIDTH`; Обязана: таблица кнопок заголовка для хит-теста
- Функция: `window_insets()`; Обязана: толщина рамки: `{top, bottom, left, right}`. По умолчанию единица со всех сторон
- Функция: `icon_grid()`; Обязана: сетка значков стола: `{w, h, left}` — шаг вправо, шаг вниз, левый край первой колонки
- Функция: `paint(state, cell_w, cell_h)`; Обязана: **только для пиксельного режима**: вернуть размещения растров и разметку попаданий. Тема, у которой её нет, в этот режим не пускается — см. «Пиксельный хром»

`state` у `bars` — `{windows, focused_id, menu_open, status, clock, tray}`;
`tray` — список `{key, text, entry, title}` в порядке появления; попадание по
пункту тема отдаёт как у часов — `{row, from, to, entry}`;
у `fill` — `{top, bottom, items, failure, selected, widgets}`; у `paint` — объединение
всего этого, разобранное в «Пиксельном хроме».
`widgets` is the list of desktop widgets in display order, in both modes; the
stock theme of this module ignores it and draws none (see "Desktop widgets").

В пиксельном режиме из этой таблицы не зовутся `window`, `bars`, `menu` и
`empty_desktop`: всё, что они рисовали, приходит растрами из `paint`. Остальное
зовётся по-прежнему — геометрия и хит-тест общие для обоих режимов.

Окно, которое приезжает в `window(canvas, window, focused)`, несёт
`window_type` — `app`, `dialog` или `tool`, как объявила его запись, — и
`opened_by`, номер окна, из которого его открыли (или `nil`). Состав
кнопок заголовка выбирает по нему тема: композитор только несёт тип от записи
до темы и не знает, во что он превращается. Пункт каталога несёт то же поле,
поэтому тема со своим меню может показывать диалоги иначе, ещё до открытия.

Значки стола: одиночный щелчок выделяет (`state.selected` — id выделенного) и
берёт значок, двойной открывает, отпускание кладёт его по сетке темы.

**Значок без координат ставит композитор**, а не оболочка: ширину экрана
знает только он, а раскладка составляется раньше, чем терминал сообщил
размер. Вычисленное место обратно не записывается — иначе первый же кадр
превратил бы автопосаженный значок в поставленный руками. Отсюда и правило
для оболочки: отсутствие `x`, `y` означает «место никто не называл», а ноль
означает место. Значок, поставленный руками, композитор не двигает никогда,
даже если экран стал уже.
Шаг сетки тема объявляет функцией `icon_grid()` → `{w, h}` (или полями
`ICON_W`, `ICON_H`): она рисует значок и знает, сколько он занимает.
Выравнивает брошенный значок композитор — иначе тот встаёт между шагами и
перекрывается попаданием соседа.

Попадание — запись `{row, from, to, …}` с одним из: `id` (поднять окно),
`index` (пункт меню), `action = "menu"` (открыть или закрыть каталог),
`entry` (открыть программу; на столе — по двойному щелчку). На панели
попадание с `entry` открывает окно одним нажатием, а если такое окно уже
есть — поднимает его и снимает свёрнутое состояние. Необязательные `title`,
`w`, `h` и `args` передаются при открытии.

Каталог может вернуть пункт `{action = "quit", title = "…"}`. Выбор мышью
или Enter запускает то же закрытие окон, что Ctrl+Q: сначала запрос закрытия,
затем обычный срок ожидания. На пустом столе выход происходит сразу.

Событие мыши `action = "wheel"` с кнопкой `wheel_up` или `wheel_down`
передаётся в содержимое окна под указателем с учётом отступов темы.
Рамка и открытое меню его внутрь не пропускают.

Что видно снаружи про меню (`desktop.list`): `menu_open`, `menu_path` — путь
раскрытой папки, `menu_choices` — сколько строк на текущем уровне,
`menu_folders` — сколько из них раскрывается. Последнее поле отвечает на вопрос,
который иначе стоит часа: **`→` молчит потому, что не сработал, или потому, что
раскрывать нечего?** Ноль папок — значит второе, и дефекта нет.

**Строки меню несут ещё три поля — по ним ходят стрелки**: `level` (номер
панели; курсор ходит по самой глубокой раскрытой), `slot` (номер строки внутри
панели) и `cursor` (та самая строка, которую тема нарисовала выбранной).
Композитор двигает `cursor` в состоянии меню и отдаёт его теме, а открывает —
**помеченную строку**, а не посчитанную заново.

**Мышь ведёт курсор наведением.** Терминал докладывает движение и без
нажатия (режим 1003), и строка под указателем становится выбранной сразу.
Каскад меняется с задержкой (`HOVER_DELAY`, 300 мс): папка под указателем
раскрывается, подменю глубже строки под указателем закрывается. Задержка не
украшение: мышь, идущая от папки к её подменю по диагонали, проходит над
соседней строкой, и без задержки закрывала бы то, куда идёт. Щелчок и клавиша
ожидающую смену снимают — они решают сами. Папка, раскрытая наведением, в
своём подменю ничего не выбирает: `menu_cursor = 0`, enter молчит, стрелка
вниз ведёт на первую строку.

Plain motion also reaches windows, so an SDK menu inside a window can follow
the pointer the same way: a motion with no button held and nothing captured is
sent to the FOCUSED window as `{type = "mouse", action = "motion", x, y}` in
its client cells, only while the pointer is over its client, and at most once
per cell. Over the frame, the desktop or a window without the focus nothing
is sent; leaving the client forgets the cell, so returning to it is sent again.
While the Start menu is open the pointer is the menu's.

Значок с подписью даёт несколько попаданий с ОДНИМ `id` — по строке рисунка и
по строкам подписи. Композитор сводит их в один значок по `id` и берёт самую
верхнюю строку: иначе стрелка вниз уходила бы с рисунка на его же подпись.

**Содержимое окна тема обрезает сама.** `canvas:put_rows` держит границу
холста, а не рамки: лишние строки лягут поверх нижней грани и ниже окна.
Обычно их нет — viewport сделан ровно в рамку, — но при смене размера
приезжает кадр прежней геометрии, и на экране это выглядит сломанной рамкой,
а не отставшим кадром.

**Разметка попаданий и отрисовка считаются по одной таблице.** Отдельная
формула для клика однажды разъедется с отрисовкой, и кнопка «закрыть»
окажется на символ левее, чем выглядит. То же про геометрию: пока она была
константой внутри композитора, панель задач снизу требовала правки
композитора — то есть механика снова знала бы про вид.

**Толщину рамки объявляет тема, а не композитор.** Из неё считаются и
размер viewport, который получает программа окна, и смещение курсора, и
наименьший размер окна. Тема с полосой заголовка внутри рамки забирает
сверху три строки; окно, посчитанное по единице, отдало бы программе на
строку больше, чем видно, а окно меньше собственной рамки дало бы viewport
нулевого размера — то есть отказ на открытии, а не кривой вид.

Тема, попросившая больше строк, чем есть на экране, не роняет композитор:
он сводит геометрию к экрану и рисует. Иначе окна уезжают за край молча.

## Desktop widgets

A desktop widget (FR-006 in `windows/shell`) is a view window without the
window: a registry entry whose process the compositor spawns like the state
provider of a view window, and whose published state the theme draws in a
panel on the desktop, under every window. The base discovers nothing and
draws nothing: the shell lists the entries, the theme draws them.

```lua
local ok, err = library.run({
    chrome = theme,
    -- The shell reads the registry (meta.type: windows.widget) and hands the list over.
    widgets = function()
        return {{entry = "app.monitor:memory", title = "Memory", w = 20, h = 6,
                 order = 20, opens = "windows.shell.taskman:window"}}, nil
    end,
})
```

- **Lifecycle.** The list is read after logon — so every widget runs under the
  logged-on user, like a window — and again on `desktop.refresh`. New entries
  are spawned, entries that vanished are stopped and forgotten, stopped ones
  are spawned again. Order: `order` (default 100), then the entry id. Ids are
  `g<n>` in the order of spawning; a respawned widget keeps its id. A provider
  that answers no list at all changes nothing: a registry hiccup must not
  blank the desktop.
- **Spawn.** `spawn_monitored(entry, workers host, compositor name, widget id,
  nil, {width, height, cell_w, cell_h})` — the call of a view window's state
  provider, with the compositor's name in the context. `width` and `height`
  are the widget's cells. A terminal resize and a changed size send the
  process a `resize` event on `window.input`, as a provider gets it.
- **Size.** `w` 10..40 and `h` 2..16 whole cells, 20×5 when not given.
  Outside the limits the widget is not spawned and not clamped — a tree laid
  out for another size would be another widget; the status line names the
  entry and the limit.
- **State.** The process publishes through `desktop.state` with its widget id,
  exactly as a view window's provider does, and only from the pid the
  compositor spawned for that widget: nobody else can draw into it. Each state
  bumps `state_revision` and redraws.
- **Stopped.** A widget whose process exits keeps its last state and gets
  `stopped = true`; the status line names the entry. `desktop.refresh` spawns
  it again.
- **Theme.** Both `fill` (cells) and `paint` (pixels) get `state.widgets`, a
  list in display order of `{id, entry, title, opens, w, h, waiting, stopped,
  content_state, state_revision}` — a view window's shape, so the SDK renderer
  takes a widget as it is. `waiting` stays true until the first state. The
  stock theme of this module does not draw widgets.
- **Hits.** A theme gives one record per widget row in `hits.desktop`: an icon
  row plus `widget = <id>`, with `entry` naming what a click opens (`opens`). A
  left press opens that window or raises the one already open, like a tray
  item — no selection, no drag, no double click. A right press offers Open,
  and without an entry nothing at all (not the desktop's Properties). The
  arrow keys walk icons only and skip widget records.
- **Status.** `desktop.list` returns `widgets = {{id, entry, title, opens, w,
  h, revision, waiting, stopped}}` — without the tree.

## Пиксельный хром: рамки картинками, содержимое символами

**Это второй режим того же контракта, а не второй композитор.** Раскладка,
геометрия, хит-тест, каталог, окна, диалоги и командный канал общие; меняется
последний слой — чем кладутся краски. Тема с полем `chrome.pixel = true` и
функцией `paint` отдаёт растры, кадр уходит как
`present(rows, {images = placements})`, а строки содержимого окон **остаются
символами**.

Почему не весь экран пикселями: bash и htop внутри окна умеют выдавать только
ячейки и меняются на каждое нажатие клавиши, а полный экран стоит 47 мс и 131 КБ
на кадр. Нарезанный по строкам хром стоит **двух растров на нажатие** — боковые
грани окна, и ничего больше; измерено на живом стенде. Замысел и все числа —
`docs/rfcs/005-pixel-chrome.md`; здесь описано то, что построено.

```lua
local ok, err = library.run({
    chrome = pixel_theme,          -- тема с chrome.pixel = true и chrome.paint
    pixels = true,                 -- РЕШЕНИЕ человека, а не наличие графики
    cell_size = gfx.cell_size,     -- спрашивает оболочка, решает механика
})
```

### Как включается и когда отказывает

**Режим включается явно.** Терминал, умеющий sixel, — не повод перерисовывать
интерфейс иначе, чем человек просил. Поэтому это параметр `run`, а не
переменная окружения: обе оболочки могут жить в разных режимах одновременно.

`run` отказывается стартовать, а не откатывается в символы молча. Отказ —
второе возвращаемое значение, и каждый называет своё:

- Что не так: у темы нет `chrome.paint`; Что отвечает `run`: «тема не умеет chrome.paint»
- Что не так: оболочка не дала `options.cell_size`; Что отвечает `run`: «оболочка не дала, чем узнать размер ячейки»
- Что не так: `cell_size()` вернул `nil`; Что отвечает `run`: причина от терминала целиком («the terminal did not say how large a cell is…»)
- Что не так: размер ячейки нулевой или отрицательный; Что отвечает `run`: названы оба числа

Тихий откат тут был бы худшим исходом: картинка не того размера выглядит как
ошибка рисования, а не как незаданный вопрос.

Для попаданий панели задач и меню `bottom_row` задаёт включительно нижнюю
строку прямоугольника. Если поля нет, попадание занимает одну строку `row`.
Один пункт меню остаётся одним попаданием с `level` и `slot`, даже когда его
рисунок занимает несколько строк: клавиатура проходит каждый пункт один раз.

### Порядок кадра

Порядок не косметика — переставь два шага, и на экране будет неправильно:

1. **Заливка.** `chrome.fill(canvas, width, height, state)` рисует фон
   стола ячейками. Зовётся в обоих режимах.
2. **Содержимое окон.** В пиксельном режиме для каждого развёрнутого окна,
   снизу вверх, композитор сначала зовёт необязательный
   `chrome.window_background(canvas, window)`, затем кладёт его содержимое
   внутрь рамки по отступам темы, обрезая лишние строки. Этот вызов позволяет
   теме закрыть текст нижнего окна фоном верхнего. Ввод мыши передаётся
   содержимому относительно первой ячейки его viewport, с учётом `left`
   и `top` из `window_insets()`.
3. **`chrome.paint(state, cell_w, cell_h)`** — тема возвращает размещения и
   разметку попаданий.
4. **Пробелы под размещениями.** Под каждой картинкой канва затирается
   пробелами. Символ, оставшийся под ней, вылезет при первой же перерисовке
   строки — и не будет виден ни на одном снимке куска.
5. **`present(rows, {cursor, images})`.**

### Что приходит теме

`chrome.paint(state, cell_w, cell_h)`; `cell_w`, `cell_h` — размер ячейки в
пикселях, тот самый, что вернул `options.cell_size`. Сама тема его не
спрашивает: на терминале без ответа она нарисовала бы не тот размер.

На каждом `resize` композитор снова вызывает `options.cell_size`, затем
`window_insets` и `layout`, пересчитывает размеры клиентов и передаёт новые
`cell_w`/`cell_h` поставщикам состояния. Это нужно и при прежнем количестве
строк и колонок: изменение шрифта терминала меняет пиксели ячейки. Если
геометрия темы зависит от ячейки, callback обновляет её до возврата размеров.
Невалидный новый размер сохраняет последнюю рабочую геометрию и показывает
причину в статусе.

`state` — объединение того, что в режиме символов приезжает тремя вызовами.
Имена полей те же нарочно: тема, умеющая оба режима, узнаёт их без перевода.

- Поле: `width`, `height`; Что это: экран в ячейках
- Поле: `top`, `bottom`; Что это: первая и последняя строка, свободные под окна
- Поле: `windows`; Что это: окна в z-порядке; последнее рисуется поверх
- Поле: `focused_id`; Что это: id фокусного окна или `nil`
- Поле: `items`, `failure`, `selected`; Что это: раскладка стола: ярлыки, причина отказа, выделенный
- Поле: `menu`; Что это: `{items, failure, open}`, либо `nil` — меню закрыто
- Поле: `status`, `clock`; Что это: строка состояния и часы
- Поле: `hint`; Что это: подсказка на пустом столе
- `widgets` — desktop widgets in display order, each shaped like a view window; see "Desktop widgets"

Окно в `state.windows` несёт: `id`, `title`, `x`, `y`, `w`, `h`, `window_type`
(`app` / `dialog` / `tool`), `opened_by`, `minimized`, `maximized`, `ready`,
`content` (`cells` / `pixels`), а для окна-вида — `render`, `waiting`,
`state_revision` и само `content_state`.

Возвращает `paint` таблицу:

```lua
{
    placements = {
        {id = "win:w1:title", raster = <gfx.Raster>, x = 10, y = 3, cols = 60, rows = 2},
        {id = "win:w1:left",  raster = <gfx.Raster>, x = 10, y = 5, cols = 1,  rows = 20},
    },
    hits = {desktop = {…}, bars = {…}, menu = {…}},
}
```

- **Координаты размещений — в ЯЧЕЙКАХ**, единичные, как везде здесь.
- **`id` обязан быть устойчивым между кадрами**: по нему поверхность узнаёт ту
  же картинку, а сменившийся id — это удаление и вставка, то есть мигание.
- **Список полон.** Размещения, которого нет в списке, не будет на экране; это
  и есть способ убрать меню — не рисовать его.
- **Растр необязателен.** Размещение без него означает «эта картинка уже на
  экране, оставь как есть». На этом стоит вся экономия — и на этом же держатся
  проверки механики, где растров нет вовсе.
- **Попадания приходят ГРУППАМИ.** Плоский список не угадывается, а вызывает
  жалобу в лог: `id` у стола, у полос и у меню значит разное, и разбор по
  догадке однажды отдал бы щелчок не тому. Записи внутри групп — те же, что в
  режиме символов.
- **Щелчок не работает — первым делом смотреть на строку состояния.** Механика
  в этом режиме не зовёт ни `bars`, ни `menu`; всё, чем ловится щелчок, приходит
  из `paint`. Тема, отдавшая попадания не в той форме, получает жалобу — и та
  идёт не только в лог (он на терминальном хосте заглушён и никому ничего не
  расскажет), но и в строку состояния. «Мышь не работает» и «попадания отданы
  плоским списком» на экране выглядят одинаково ровно до этой строки.
- **Разметку стола могут вернуть оба** — и `fill`, и `paint`. Значки в этом
  режиме рисует `paint`, поэтому его разметка старше; если он её не вернул,
  остаётся та, что вернула заливка.

В пиксельном режиме НЕ зовутся `chrome.window`, `chrome.bars`, `chrome.menu` и
`chrome.empty_desktop` — всё это рисует `paint`. Зовутся по-прежнему
`chrome.layout`, `chrome.window_insets`, `chrome.icon_grid`,
`chrome.title_button_at` и `chrome.fill`: **геометрия и хит-тест общие**, они
про координаты, а не про краски. Это и есть причина, по которой переход
дешёвый.

### Что композитор делает сам

- Что: Кладёт строки окон в канву; Почему так: растровая тема в канву не пишет, а bash умеет только ячейки
- Что: Кладёт пробелы под размещениями; Почему так: символ под картинкой вылезет при перерисовке строки
- Что: Отбрасывает негодные размещения, называя каждое; Почему так: `present` отвергает КАДР целиком, а композитор зовёт его через `assert`: тема с одной опечаткой погасила бы весь стол
- Что: Ловит повтор `id` в одном кадре; Почему так: два размещения с одним именем — спор о том, что показать, на экране он выглядит миганием
- Что: Отдаёт цену кадра в `desktop.list`; Почему так: неверно порезанный хром рисует ПРАВИЛЬНЫЙ экран, просто медленный, — у медленного нет ни стека, ни симптома

### Чего композитор не может, и почему

- **Создать растр.** Растр — это модуль `gfx`, а запись, объявившая недоступный
  модуль, роняет боот ЦЕЛИКОМ: `node with ID {gfx :gfx} not found`. Измерено на
  установленной сборке. Объяви механика `gfx` — она стала бы негодной везде, где
  графики нет, включая тех, кому пиксели не нужны. Правило стенда: **`gfx`
  объявляет только тот, кто без него не существует.** Пиксельная тема — да,
  механика — нет.
- **Загрузить библиотеку по имени из реестра.** Импорты объявляются записью,
  динамического `require` нет. Поэтому `render` окна-вида зовёт тема, которая
  его импортирует, а композитор несёт до неё только состояние.
- **Растеризовать содержимое окна.** Оно остаётся символами; растеризатор
  строки со стилями тут не нужен вовсе — и это не упущение, а то, ради чего всё
  считалось: полный экран пикселями стоит 47 мс на каждое нажатие клавиши.

### Цена кадра и чем её мерить

`frame` в ответе `desktop.list`: `changed_rows`, `bytes_written`, `images` —
сколько размещений объявил кадр, и `placements_sent` — сколько растров рантайм
отправил на самом деле. Последнего поля нет в старых сборках, и **пустое поле
означает «не измеряли», а не ноль**: иначе старый рантайм молча выдавал бы себя
за идеальный.

Мерить им «тихий кадр» может только тема с настоящими растрами: у темы без них
ноль получится при любой ошибке нарезки. Поэтому такой проверки в этом модуле
нет намеренно — это критерий пиксельной темы, а не механики.

### Что проверено и что проверить нельзя

Уровней три, и первые два взаимно слепы. Это не оговорка, а причина, по которой
за одну ночь трижды находилось то, чего не показал ни один зелёный набор:

- Уровень: Части; Что видит: раскладка, перекрытия, попадания; Чем проверяется: пробник темы, чистый Lua
- Уровень: Целое состояние; Что видит: что открылось, что связалось, куда уехал фокус, что под картинкой пробелы; Чем проверяется: живой композитор в тесте (см. «Разработка»)
- Уровень: Целый вид; Что видит: глиф, грань, цвет, залито ли тело окна; Чем проверяется: глаза человека или PNG

Зелёный набор проверок механики ничего не говорит о виде: растров в нём нет и
быть не может. Ровно поэтому снимок ЦЕЛОГО экрана однажды нашёл три дефекта, ни
один из которых не показал снимок куска.

## Устройство

Сверху вниз — от механики к тому, что её зовёт:

- `src/desktop/library.lua` — **механика**: окна в z-порядке, ввод, хит-тест, команды, сборка кадра. Вида не знает
- `src/desktop/desktop.lua` — **штатная оболочка**: выбор темы и имени, больше ничего
- `src/desktop/chrome.lua` — **штатная тема**: рамки, заголовки, кнопки, полоса окон, меню; чистые строки без вызовов в рантайм
- `src/desktop/window_api.lua` — что окно может попросить у десктопа: открыть, закрыть, поднять, спросить. Имя композитора берёт из контекста процесса
- `src/desktop/programs.lua` — что запись реестра говорит о своей программе: тип окна, «показывать в меню», чем рисуется содержимое. Чистые таблицы
- `src/desktop/pixels.lua` — сборка пиксельного кадра: пробелы под картинками, разбор размещений и попаданий. Чистая арифметика
- `src/desktop/window_pty.lua` — окно с настоящей программой: отдаёт свой порт под PTY
- `src/api/` — командный канал, мастерская и их политики
- `src/persist/` — хранилище окон, сборка записи реестра и загрузчик
- `src/migrations/` — таблица окон, собранных в рантайме
- `src/security/` — политики: композитору, каналу, мастерской, окнам, доступу

Две библиотеки вынесены из механики не ради красоты: `programs` и `pixels` —
чистые функции без рантайма, и потому проверяются прямо, без терминала и без
графики. Всё, что осталось в `library.lua`, проверяется только живым
композитором (см. «Разработка»).

Права разделены нарочно. Композитору нужно порождать процессы и запускать
программы; командному каналу — только найти композитор и заговорить с ним.
Право `spawn` у ручки означало бы, что HTTP-запрос запускает программы мимо
единственного места, которое их считает.

## Разработка

```bash
make setup     # разрешить зависимости модуля и харнесса
make lint      # wippy lint
make test      # автономный харнесс: форма реестра И живые композиторы
make verify    # всё вместе
```

Набор — полсотни проверок за несколько секунд, и он не сводится к форме
реестра: половина поднимает НАСТОЯЩИЙ композитор на viewport, щёлкает в него
мышью и жмёт клавиши. Как это устроено — ниже, в «Композитор поднимается прямо
в тесте».

Разделы после — правила, и каждое куплено за конкретную ошибку. Читаются они
как список симптомов, ни один из которых не похож на свою причину.

Харнесс в `test/` подменяет модуль рабочей копией из `..`, поэтому он же
поднимает десктоп без всякого приложения:

```bash
cd test && wippy run --host windows.tui_desktop:terminal desktop
```

Полноэкранную программу нельзя проверить кодом возврата: без настоящего
терминала она не запускается вовсе, а запущенная пишет не строки, а поток с
абсолютным позиционированием. Пробник [`tools/tui-probe.py`](tools/tui-probe.py)
даёт PTY заданного размера, печатает по сценарию и разбирает поток в текстовую
сетку — снимок экрана и есть доказательство.

```bash
cd test && python3 ../tools/tui-probe.py --cols 100 --rows 26 --boot 60 \
    --send $'\033n' --send 'echo ok' --send-key enter --expect 'ok' \
    -- wippy run --host windows.tui_desktop:terminal desktop
```

### Право под каждый объявленный модуль — правилом, а не глазами

Объявленный модуль без права **не отказывает громко**. `env.get` отдаёт `nil`,
и соседнее `or умолчание` превращает отказ по правам в «никто ничего не
назначал»; `db.get` роняет чтение уже в работе, когда виноватым выглядит
запрос. Здесь это стоило одной молчащей настройки: композитор объявлял `env`,
права не имел, и переназначенное имя базы окон не работало.

Проверяется правилом по всему реестру модуля: у записи, которая несёт свои
политики, для каждого модуля из закрытых правами (`env`, `fs`, `sql`,
`registry`, `exec`) обязано быть выдано хотя бы одно открывающее действие.
Отказ называет запись, модуль и следствие. Отдельным правилом то же проверяется
для белого списка модулей окна, собранного в мастерской: политика у него одна и
известна заранее.

Библиотеки правило не трогает: своих политик они не несут и работают в правах
того, кто их позвал.

### Композитор поднимается прямо в тесте

Полтора дня здесь исходили из того, что механику без настоящего терминала не
проверить, и весь класс проверок — z-порядок, фокус, каскад закрытия, resize,
перетаскивание — считался доступным только глазом через пробник. Это неверно.

**Экран композитора не обязан быть терминалом.** `tty.viewport` создаётся прямо
в тестовой функции, `view:grant()` отдаёт его порождаемому процессу — тому же
механизмом, которым композитор раздаёт экраны своим окнам, — и внутри едет
`library.run` со штатной темой. Дальше с ним говорят так же, как командный
канал снаружи, а щелчки едут в его экран настоящими событиями мыши через
`view:send`.

```lua
local view = tty.viewport({width = 80, height = 24})
local pid = process.with_options({terminal = view:grant()})
    :spawn_monitored("app:test_composer", "app:processes", "имя.композитора")
-- ждать не наугад, а появления имени в реестре процессов:
process.registry.lookup("имя.композитора")

view:send({type = "mouse", action = "press", button = "left", x = 4, y = 8})
process.send("имя.композитора", "desktop.list", {reply_to = tostring(process.pid())})
```

Так проверены родство диалога с его окном, поднятие окна щелчком, порядок z,
переход фокуса при закрытии верхнего окна и видимость отказа на команду без
обратного адреса. Живой пример целиком — `test/src/wiring_test.lua` и
`test/src/test_composer.lua`.

Две вещи, без которых это не работает:

- **Ждать надо событие, а не время.** Композитор появляется в реестре
  процессов, когда готов принимать команды, — это и есть сигнал. Готовность
  щелчка проверяется тем же способом: у композитора есть строка состояния,
  которую щелчок по пустому столу очищает, и её исчезновение — веха, по
  которой видно, что событие обработано. Проверки на время врут.
- **Проверка не должна заводить себе способ нажать.** Кнопки открываются
  мышью, потому что мышью их открывает человек; цифровые сокращения в
  интерфейсе, заведённые ради проверки, — это ограничение инструмента,
  протёкшее в продукт.

### Невызванная функция зелёная в любом наборе

Функция, которую не зовёт никто, проходит любой набор проверок — а падает на
первом же настоящем вызове, обычно у другого человека. За одну ночь это
случилось дважды: заливка стола, которую композитор начал звать, упала сразу же,
а до того была «рабочей»; и три поздних `local` (см. ниже).

Поэтому у вынесенных библиотек (`pixels`, `programs`) есть правило: список
экспортированных функций сверяется со списком покрытого, и новая функция без
проверки красит набор. Для путей внутри композитора такого правила нет —
приходится проходить их глазами; так нашлись три непроверенных: неизвестное
`window_content`, смерть поставщика состояния и `resize` окна-вида, у которого
нет viewport'а.

### Всё, что зовётся из функции, объявляется выше неё

Стоило часа ложного следа, и симптом на причину не указывал: `local function
forget` стоял НИЖЕ `close_window`, который его зовёт, — значит внутри неё это
глобальная переменная, то есть `nil`. Падало ровно на закрытии окна-вида,
единственного пути, где `close_window` зовёт `forget` напрямую.

**Снаружи упавший композитор выглядит как проблема доставки сообщений**: имя в
реестре осталось, экран держит последний кадр, а ответов нет — и час уходит на
поиск гонки, которой не существует. Прежде чем искать её, посмотрите на ЭКРАН
композитора: в тесте это `view:snapshot(-1)`, и там сразу видно и строку
состояния, и живые окна.

Взаимная рекурсия чинится предобъявлением: `local forget: any` выше обеих
функций, `forget = function(window)` ниже.

### Две ловушки, стоившие здесь времени

**Хвостовой вызов.** В go-lua v1.5.18 вызов yield-функции, стоящий последним
как `return f(...)`, не выполняется вовсе — молча, за 0 мс, с пустым
результатом. Такую форму имеют все вызовы этого стека: `tty.start`,
`surface:present`, `viewport:send`, `session:send`. Поэтому они обёрнуты в
`assert(...)`: это не стиль, это обход.

**Экран без размера.** Запуск не из терминала (скрипт, CI, пайп) отвечает на
`screen_size()` нулями, и холст такую ширину отвергает — композитор падал на
первой же строке. Геометрия поэтому проверяется, а не берётся на веру.

## Вход в систему

Композитор работает под служебным актором из `meta.command.security`, и без
входа под ним же работало бы каждое окно. `options.logon` — функция оболочки,
которую композитор зовёт **до первого кадра стола и до чтения команд**: окно,
открытое каналом раньше входа, родилось бы без личности.

```lua
library.run({chrome = theme, logon = function(screen) … end})
```

`screen` — то, чем диалог рисует себя на том же терминале: `events` (канал
`tty`), `width`, `height`, `canvas`, `pixels` (режим кадра), `cell()` — размер
ячейки, `resize()` — перечитать размер и пересоздать холст (звать на событии
`resize`), `present(painted)` — показать кадр; в пиксельном режиме `painted`
несёт `placements`, как у `paint`.

Функция возвращает `{actor, scope, context}` либо `nil, причина`. Под
`actor`/`scope` композитор порождает **каждое** окно — и поставщик состояния
окна-вида, и процесс с viewport; `context` дописывается в контекст процесса
окна (обычно `user_id`, `user_name`) и читается модулем `ctx`. Сам композитор
под своим актором остаётся: реестр и хранилище окон он трогает своими правами.

- **Отказ входа — выход, а не стол под служебным актором.** Стол без
  пользователя выглядел бы вошедшим, а окна работали бы от имени процесса.
- **Личность фиксируется в момент порождения.** Открытые окна при смене
  пользователя не «переезжают»; смена — закрыть окна и войти заново.
- **Окно наследует скоуп с добавкой**: политики его записи дописываются к
  скоупу пользователя. Это касается и окон мастерской.
- Композитору нужно право `process.security` — оно в `desktop_runtime`.
- `desktop.list` отдаёт `user = {id, name}`: снаружи это единственный способ
  отличить окна под пользователем от окон под служебным актором.

### A window that only some people may open: `meta.requires`

An entry may name the action a person needs to open it. The compositor asks
the logged-on identity's scope (`scope:evaluate(actor, action, entry)`) before
spawning, and refuses with the person, the entry and the action named — on
the desktop's notice line for alt+n and the menu, in the reply for
`desktop.open`. A desktop without logon asks nobody, as before.

`window_pty` declares `requires: tui_desktop.pty`: the program runs under the
entry's own policy (exec), that is, a shell on the server under the OS
account, whoever logged on. An application grants the action to the people
who may have it.

## Several desktops in one runtime

A runtime serving remote terminals (the `terminal.ssh` host) runs one desktop
per connection. They answer to one family of names: a compositor claims the
first free of `name`, `name.2` … `name.<service_slots>` (default
`window_api.DESKTOP_SLOTS`, 16), and the registry releases a name with its
process, so a number is reused. The process registry has no listing, so this
rule is the directory, and it lives in one place:

- `window_api.desktop_names(family, slots?)` — every name of the family;
- `window_api.desktops(name)` — the ones running now, `{name, pid}` each,
  the unnumbered first; a numbered name counts as its family
  (`window_api.desktop_family`);
- `desktop.list` answers `service` — the name this desktop claimed — and each
  window's `pid`.

Whoever addresses "the desktop" from outside (a tray item, a refresh, the
workshop) iterates `desktops(family)`: one name would reach the first
connection only.

### A desktop whose terminal went away closes its windows

A connection drops. The desktop ends as "Shut Down" does — windows closed,
not left running with nobody to see them (a bash among them) — on either of
two signals:

- **CANCEL** (`process.event.CANCEL`): the `terminal.ssh` host asks the
  program to finish when its client leaves; the runtime does the same when it
  stops.
- **A frame that could not be written.** `out:present` failing means the
  terminal is gone; the compositor stops drawing, closes its windows and
  exits. It used to `assert` there, and the windows outlived it.

The cleanup after either writes nothing to the terminal that is gone, so the
desktop ends with success, not with the error of a write nobody could read.
